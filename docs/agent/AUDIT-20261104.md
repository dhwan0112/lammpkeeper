## A-1 · P2 · Dumps written with `dump_modify units yes` / `time yes` cannot be loaded
- Where: lammps_post/parsers.py:366-376 (`_read_layout`), 713-717 (`__iter__`), 520-545 (`index`/`_find_frame_marker`).
- What: `_read_layout` accepts only `ITEM: TIMESTEP` as the first non-blank line and raises `invalid dump header` for anything else. LAMMPS (since 2021) writes optional `ITEM: UNITS` + units word and `ITEM: TIME` + float before `ITEM: TIMESTEP` when `dump_modify units yes` / `time yes` are set (and before every frame). The streaming loop at 713-717 would likewise reject them as "unexpected atom lines or frame header" in later frames, and the index path would fold them into the previous frame's atom block as surplus rows.
- Trigger: first lines `ITEM: UNITS\nmetal\nITEM: TIME\n0.5\nITEM: TIMESTEP ...`. Confirmed: `DumpReader(path)` -> `ValueError: invalid dump header: ITEM: UNITS`.
- Effect: visible crash (not silent), but a dump that carries exactly the explicit units/time evidence this project wants (ADR-0005) cannot be read at all, and the message does not say the header is a valid optional LAMMPS item.
- Known?: new
- Test coverage: none (grep of tests/ and docs/ for `ITEM: UNITS` / `dump_modify.*units` finds nothing).
- Confidence: high on the reject (reproduced); medium on the LAMMPS format detail (from memory of the dump docs, not rechecked online).

## A-2 · P3 · Streaming and indexed (LazyFrames) paths disagree on blank lines between/after frames
- Where: lammps_post/parsers.py:707-712 (stream skips blank lines before a marker), 786-792 (`_parse_block` rejects any blank row), 521-547 (`index` block_end = next marker or EOF), 549-553 comment in `_find_frame_marker` claiming the paths "agree on frame boundaries".
- What: the stream path `continue`s on blank lines between frames and at EOF; the index path makes the block span everything up to the next `ITEM: TIMESTEP`/EOF, so a blank line after the last atom row makes `len(lines) != natoms` or `any(not row.strip())` fire.
- Trigger: a frame followed by a blank line (hand-edited, concatenated, or `cat`-ed dumps; trailing blank line at EOF). Confirmed: `[f['timestep'] for f in DumpReader(p)]` -> `[0, 10]`, `LazyFrames(DumpReader(p))` -> `ValueError ... invalid atom lines, expected 2` (both for blank-between and blank-at-EOF).
- Effect: same file loads via `parse_dump`/`DumpReader` but fails in the shell (which uses LazyFrames, shell.py:640-644). Visible, not wrong numbers, but the contract in the comment is false.
- Known?: new
- Test coverage: tests/test_dump_reader.py covers stride/max_frames and truncation, not blank-line agreement between the two paths.
- Confidence: high (reproduced).

## A-3 · P3 · Any mid-run timestep change makes the whole log (and input) unparseable
- Where: lammps_post/parsers.py:1259-1272 (`parse_log` raises "changing timestep requires separate thermo timelines"), 2124-2131 (`parse_input` raises "timestep declared twice with different values"), 1252-1255 (mixed `units`).
- What: realistic multi-stage workflows (small timestep for minimization/soft start, larger for production; `timestep 0.0005` then `timestep 0.001`) raise a ValueError for the entire file instead of returning per-block timesteps or an unresolved dt. This is the strict, visible behavior ADR-0005 chose, so nothing is silently wrong, but it makes the log/input unusable and there is no per-block escape.
- Trigger: log with `timestep 0.0005 ... run ... timestep 0.001 ... run`. Confirmed: `ValueError: changing timestep requires separate thermo timelines`.
- Effect: user cannot load thermo from such a run at all; dt_fs cannot be resolved even for the unambiguous block.
- Known?: new (design decision, listed for the maintainer to confirm it is intended)
- Test coverage: tests/test_execution_contract.py:394,423 use a `changing.log` but for other changes; no test pins this message for logs.
- Confidence: high on behavior, low on whether it should change.

## B-1 · P2 · MSD of an NPT/orthogonal-variable-box trajectory includes affine box scaling (previously drafted issue 2, still present)
- Where: lammps_post/analysis.py:1618-1634 (delta = cur_pos - prev_pos, MIC with current-frame lengths, accumulated); docstring 1462-1474 admits it.
- What: Per-step displacement is taken in lab coordinates of wrapped positions. When the box length changes between dumps, an atom that is fixed in fractional coordinates still moves by s*(L'-L); that is added to `unwrapped`. No fractional-coordinate or COM correction exists.
- Trigger: any barostat run (npt) or any variable-box series, orthogonal path (the triclinic path rejects variable cells).
- Effect: static lattice with box 10 -> 10.2 -> 10.4 A and fixed fractions gives msd = [0, 0.0338, 0.1352] A^2 (repro run; true MSD is 0 in the comoving frame). Diffusion/MSD slopes for solids under NPT are inflated by an amount comparable to the signal (draft measured 2.3% box change, 0.37 A scaling shift vs 0.0746 A^2 end value on the ACE fixture).
- Known?: previously drafted issue 2 (affine/COM drift). Not an open REV row in open-review-rows.md.
- Test coverage: tests/test_msd.py and the slow golden msd_O/msd_FeUp in tests/test_regression_numeric.py (GOLDEN_SLOW) cover nearby; none asserts a comoving frame. A fix as an option leaves the golden unchanged; changing the default would change the msd goldens and the verify-skill variable_box_msd expectation.
- Confidence: high (reproduced, documented limitation, so the risk is a user reading the number as a diffusion MSD).

## B-5 · P3 · geometry.wrap_positions perturbs non-periodic coordinates at the ulp level and is unused in production

- Trigger: a dump atom row such as `1<NBSP>1 0.1 0.2 0.3 0 0 0` read with `columns=['x','y','z']`. Verified through the real reader: native gives `[[0.2,0.3,0.0],...]`, `LKPR_NO_NATIVE=1` gives `[[0.1,0.2,0.3],...]`. With all columns selected both paths agree, because the fallback triggers.
- Effect: silently wrong coordinates, only when the native extension is installed and the file has exotic whitespace (for example copied from a rich-text document). It breaks the "native and fallback identical" requirement. The fix is to make both sides use the same tokenisation, or to reject non-ASCII whitespace in the shared check at parsers.py:654-665.
- Known?: new
- Test coverage: none (grep of tests/ finds no NBSP or Unicode-space case). tests/test_dump_reader.py and test_row_width.py cover width and parity nearby, but not this.
- Confidence: high, reproduced on the real reader.

## E-2 · P3 · lkpr-rs panics (exit 101) on a non-UTF-8 command-line argument
- Where: rust/lkpr-rs/src/main.rs:445 (`std::env::args()`); also :137-143 (`env::var("LKPR_PYTHON")`).
- What: `std::env::args()` panics if any argument is not valid Unicode. The fix is `args_os()` with an explicit usage error.
- Trigger: `lkpr-rs thermo-summary --log $'\xff.log' --python PY`.
- Effect: a Rust panic and exit 101 instead of a usage error (2) or failure (1).
- Known?: new
- Test coverage: none (tests/cli.rs and tests/test_rust_cli.py cover spaces only, via `a b.log` and a symlink path with spaces).
- Confidence: high on the documented std behaviour. Not run (no cargo).

## E-3 · P3 · Human-readable output to a closed or full stdout panics after the job ran
- Where: rust/lkpr-rs/src/main.rs:245-271 (doctor), :311-387 (print_summary, print_table), :448/:452 (help and version). All use `println!`.
- What: Rust ignores SIGPIPE, so `println!` on EPIPE or ENOSPC panics ("failed printing to stdout"), exit 101. The 2026-11-01 audit fixed this only for `--json` via `print_raw`. The default human mode is unprotected, and `eprintln!` at :468 has the same property.
- Trigger: `lkpr-rs thermo-summary ... | head -0`, or stdout redirected to /dev/full.
- Effect: panic text and exit 101 after a completed job, instead of the structured `output_write_failed` and exit 1 that `--json` gives.
- Known?: new (the JSON half was fixed in AUDIT-20261101)
- Test coverage: tests/cli.rs:163 `json_mode_write_failure_is_not_success` covers `--json` only.
- Confidence: high on the mechanism, medium on the exact exit code (not run).

## E-4 · P3 · Backend that exits normally while a descendant holds stdout open leaves that descendant running
- Where: rust/lkpr-rs/src/backend.rs:155-229 (`supervise`) against :135-145 (`terminate`, whose comment says a group kill stops pipe holders).
- What: The group SIGKILL happens only on the forced paths (overflow, deadline). When the leader exits on its own, `try_wait` reaps it and the loop breaks. If a group member still holds the pipe, `recv_timeout(5 s)` expires and `backend_stdout_held_open` is reported. No signal is sent to the group, so the straggler keeps running, and the reader thread stays blocked.
- Trigger: a backend (or a misbehaving Python hook) that forks a long-lived child inheriting stdout, then exits.
- Effect: exit 1 with a clear message, but an orphan process is left behind. This is consistent with the "reported, not waited out" design, but the cleanup claim in the `terminate` comment does not extend to this path.
- Known?: new
- Test coverage: tests/cli.rs:473 `stdout_held_open_after_exit_is_reported_not_waited_forever` covers the report but not the survivor.
- Confidence: medium. Reading shows no kill on this path. Whether to kill is a design choice.

## E-6 · P3 · A KeyboardInterrupt during parse is converted to InputChangedError when the file also changed

## Not findings
- Registration: all 69 entries in tests/run.py MODULES are unique, and all 69 `tests/test_*.py` files are registered, with no stale names.
- Rust/Python contract: field names and types parse correctly. `job_schema_version`, `state`, `backend_response.{result,warnings,provenance}`, `cleanup.status`, `diagnostics.{handshake,execution}` and `error.{code,message}` match jobs.py's `_data` and execution.py's envelope. The version checks use `as_u64` and `== 1` on arbitrary_precision numbers, which parse correctly. Large integers and `-0.0` keep their digits (unit test `number_text_keeps_original_digits`).
- `--timeout`: Rust's finite-positive rule matches `_duration`. `f64::to_string` output is parsed by Python's float parser. Overflow is rejected before any `Duration` or `Instant` arithmetic (`deadline_after`).
- Lifecycle in backend.rs: the leader is not reaped before the group kill, so there is no pid or pgid reuse window. The reader thread keeps draining after overflow. stderr is inherited, so no stderr-fill deadlock is possible. The stdin writer thread cannot block the loop. Every path after `spawn` reaches `supervise`, which reaps the child, so there are no zombies on error paths. The detached threads are bounded by the process exit.
- SIGINT is handled with `SA_RESTART`, forwarded once to the direct child, and followed by a 10 s grace. SIGTERM/SIGHUP to lkpr-rs not being forwarded is a documented known limit (docs/agent/UI-1.md "Known limits"), not re-reported.
- Exit codes: 0/1/2/130 match the USAGE text and docs/agent/UI-1.md. Failures after Ctrl-C are mapped to 130 in `main`.
- Native vs NumPy numerics: probed `1e39`, `1e-50`, `inf`, `nan`, `Infinity`, `+.5e1`, `5.`, `0x10`, `1_0`, `1d3`, full-width digits, and float32 halfway cases. Both paths agree on results and on error vs success. float32 narrows via f64, as in loadtxt.
- Native row handling: blank lines are rejected earlier in Python. `\r\n` rows agree. `usecols` with the element column is consistent with `ncols`. The Python reader never calls `parse_block` with an element column outside `usecols`.
- Unreachable via the reader: `parse_block(b"Fe 1\n", 1, [], 0, False)` panics (`usize` underflow in lib.rs:105) because `usecols.len() - 1` wraps. The Python reader always includes the element column, so this is only a hardening note.
- native/build.sh uses `set -euo pipefail` and builds from the script's own directory. It only handles Linux `.so`, which is documented. The `abi3-py39` and `pyo3` 0.26 `detach` usage is consistent.
- execution.py: strict JSON (duplicate keys, nonfinite numbers, float overflow), the 1 MiB bound, the NUL check, the bounded request ID, the warning cap with a notice, the stdout redirect and `ensure_ascii` output all behave as the capabilities document claims. The `error_codes` list matches the codes used.
- application.py: step precision, header collision, finiteness and overflow-to-error checks are correct. The stat-identity wrapper is documented as not content-hashed.
- cli.py and shell.py: routing, the no-argument non-tty help (exit 0) and the unknown-command argparse exit 2 are fine. History snapshot and restore in `_enter` and `_run` are correct. KeyboardInterrupt is handled.
- verify_refs.py: schema validation, ERROR on missing or malformed references, ERROR on unlisted measured keys, NaN yielding FAIL, and shape mismatch yielding FAIL all avoid false PASS. `--only` with an unknown id exits 2. verify.sh: unique evidence names via noclobber claims, `PASS tests` requires both exit 0 and a `N passed, 0 failed` line, and SKIP lines are surfaced.
